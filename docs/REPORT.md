# Сопроводительная документация
## 1. Назначение

Получение основных метаданных изображений из файлов без декодирования полного растра. Для каждого файла отображаются имя, путь, формат, ширина/высота, физическое разрешение X/Y, глубина, сжатие. Дополнительно показываются параметры, определённые в конкретном формате.

## 2. Технологии и внешние библиотеки

- React — построение UI, управление состоянием и отображение таблицы.
- TypeScript — типы, общий контракт Metadata/Result, описание слоёв.
- Vite и @vitejs/plugin-react — dev-сервер, сборка и worker bundles.
- Web Workers — независимые потоки обработки в браузере.
- File/Blob.slice()/arrayBuffer(), DataView — чтение небольших частей бинарных файлов.
- Виртуализация таблицы реализована самостоятельно: DOM содержит только строки видимого диапазона плюс запас 6 строк с каждой стороны.
- Внешняя библиотека для извлечения метаданных НЕ применяется. Каждый парсер написан вручную. Просмотр картинки выполняется браузерным img и не участвует в чтении метаданных.
- Для тестов: node:test, assert, tsx. Pillow и tifffile использовались только при подготовке тестовых изображений, в приложении и в его зависимостях их нет.

## 3. Три независимых слоя

Presentation получает результаты через callback Engine, хранит состояние интерфейса, фильтрует и сортирует результат, виртуализирует строки, выводит прогресс, по клику создаёт object URL для превью. В UI нет DataView и кодов TIFF/JPEG-тегов.

Core определяет DTO, InspectorPort, BatchEngine, Job/Progress. collectJobs формирует очередь из переданного браузером списка и сохраняет webkitRelativePath. Сам обход дерева файловой системы при выборе папки делает браузер: веб-приложению передаётся плоский FileList со вложенными относительными путями. Engine назначает задания свободным workers, собирает результаты, обновляет прогресс партиями каждые 100 мс, ограничивает число параллельных заданий и умеет отменять обработку. Engine знает только протокол Job → Result и фабрику worker, а не реализации парсеров.

Infrastructure содержит BinaryInspector, реализующий InspectorPort; маршрутизатор определяет формат по сигнатуре. Отдельные функции parseJPEG/PNG/GIF/BMP/TIFF/PCX читают поля через общий Reader. parser.worker.ts служит адаптером между протоколом worker и BinaryInspector. Ошибка конкретного файла превращается в Result.error; ошибочный файл не останавливает остальные.

composition.ts — единственная точка связывания Engine с адресом worker-модуля. Направление зависимостей: Presentation → Core, Infrastructure → контракты Core. Core не импортирует Infrastructure; парсеры не зависят от React.

## 4. Поля и источники

### JPEG

- Маркер SOI FF D8 определяет формат.
- В SOF читаются precision, height, width, components. Глубина = precision × components. Обычный 8-битный трёхкомпонентный JPEG даёт 24 bpp; grayscale даёт 8 bpp. Это представление компонентов до сжатия, не среднее число бит сжатого файла и не строго название цветового пространства.
- В APP0 с идентификатором JFIF читаются units, Xdensity, Ydensity. Units=1 — на дюйм; units=2 — на сантиметр, умножение на 2.54; units=0 — только отношение сторон, физический DPI не задан.
- В APP1 Exif читается TIFF IFD0: XResolution=282, YResolution=283, ResolutionUnit=296. Exif с физическими значениями имеет приоритет над JFIF. При различии более 0.1 dpi показывается предупреждение. Вторая ось не выдумывается, если в Exif она отсутствует.
- SOF определяет baseline/extended/progressive/lossless семейство; для DCT показывается сжатие с потерями, для lossless SOF — без потерь.
- В DQT читаются 64 коэффициента и номер таблицы. Они управляют величиной квантования DCT-коэффициентов. Порядок вывода — zigzag из файла, НЕ обычная построчная матрица 8×8. Процент качества не вычисляется: это не стандартное поле JPEG.
- При чтении встреченного SOS сканирование останавливается: сжатые пиксели не нужны. DNL, иерархические многокадровые особенности и метаданные после первого SOS не обрабатываются. JPEG XL/JPEG 2000 не являются поддерживаемым JPG.

### PNG

- Сигнатура PNG; IHDR: width, height, bit depth, color type, compression, interlace.
- Глубина = bit depth × количество компонентов: gray=1, RGB=3, indexed=1, gray+alpha=2, RGBA=4. Для indexed это глубина ИНДЕКСА, а не RGB-цвета палитры. tRNS не добавляет бит к глубине.
- В pHYs хранятся pixels-per-unit X/Y и единица. При unit=1 используется метр: DPI = px/m × 0.0254. При unit=0 известны только пропорции. При отсутствии pHYs физическое разрешение неизвестно.
- Compression method=0 означает Deflate, без потерь.
- PLTE: число записей = длина блока / 3; это размер таблицы, не фактически использованное количество уникальных цветов.
- Interlace=1 означает Adam7.
- Сканируются заголовки chunks до IEND; большие IDAT пропускаются по длине, поэтому pHYs обнаруживается и после IDAT. CRC не вычисляется. eXIf в PNG не разбирается; APNG-анимация не анализируется.

### GIF

- GIF87a/GIF89a и Logical Screen Descriptor дают ширину и высоту ЛОГИЧЕСКОГО ХОЛСТА.
- В GIF нет стандартного физического DPI. Pixel Aspect Ratio — отношение размеров пикселя, не dots/inch.
- Первый Image Descriptor даёт размер первого кадра и наличие локальной палитры. Если она есть, её размер определяет глубину; иначе используется глобальная палитра.
- Бит на индекс = SizeOfColorTable + 1; цветов палитры = 2^bits. GIF Color Resolution — другое поле: исходное число бит на основной цвет минус 1; его нельзя принимать за bpp индексного изображения.
- LZW — стандартное сжатие GIF, без потерь. Само превращение RGB в палитру при создании GIF может терять цвета, это не потеря на этапе LZW.
- Кадры после первого не просматриваются, количество кадров не заявляется. Если у следующих кадров другие палитры, глубина в таблице остаётся характеристикой первого кадра.

### TIFF / BigTIFF

- II/MM определяют порядок байтов, magic=42 — Classic TIFF, magic=43 — BigTIFF. Поддерживаются оба порядка байтов, 32/64-битные смещения с проверкой безопасного JS-диапазона.
- Первый IFD: ImageWidth=256, ImageLength=257, BitsPerSample=258, Compression=259, PhotometricInterpretation=262, SamplesPerPixel=277, XResolution=282, YResolution=283, ResolutionUnit=296.
- Глубина = сумма BitsPerSample; если передано одно значение для одинаковых компонентов, оно умножается на SamplesPerPixel. Стандартные defaults: BitsPerSample=1, SamplesPerPixel=1, Compression=1, ResolutionUnit=2.
- Unit=2 — дюйм; unit=3 — сантиметр × 2.54; unit=1 — без абсолютной единицы, DPI неизвестен. Отсутствие X/YResolution не заменяется на произвольные 72 или 96.
- Compression показывается как название алгоритма: none, CCITT, LZW, JPEG, Deflate, PackBits и др.; неизвестный код не маскируется и выводится числом.
- ColorMap=320: число цветов = число значений / 3 (по отдельному массиву R/G/B).
- PhotometricInterpretation — числовой код трактовки цветовых компонентов, например 2=RGB, 3=palette, 5=CMYK, 6=YCbCr. Orientation=274 — инструкция ориентации: 1=обычно, 6=поворот 90° по часовой стрелке и т.д. В таблице размеры из файла, без поворота.
- Анализируется только первая страница. Сжатые strips/tiles, SubIFD, дополнительные страницы не декодируются.

### BMP

- BM и DIB header size; поддержаны BITMAPCOREHEADER=12 и Windows DIB 40/52/56/108/124.
- Width/Height, biBitCount, biCompression читаются из DIB. Отрицательная высота означает top-down; в таблице отображается абсолютная высота.
- DPI = biXPelsPerMeter / biYPelsPerMeter × 0.0254. В COREHEADER этих полей нет.
- BI_RGB=0 — без сжатия; RLE8=1; RLE4=2; BI_BITFIELDS=3 — тоже без сжатия, но с цветовыми масками; JPEG=4, PNG=5, ALPHABITFIELDS=6.
- Если глубина для встроенного сжатого формата равна 0, она показывается неизвестной, вложенный поток не декодируется.
- biClrUsed — размер палитры; для индексных форматов при 0 берётся 2^bpp.
- 32 bpp не гарантирует реально используемый alpha-канал.
- OS/2 2.x DIB=64 и прочие неподдерживаемые варианты дают явную ошибку, а не неверные поля Windows-заголовка.

### PCX

- Manufacturer=0x0A, фиксированный 128-байтный заголовок.
- Width = Xmax-Xmin+1, Height = Ymax-Ymin+1: границы включительны.
- Глубина = BitsPerPixel (на ОДНУ плоскость) × NPlanes.
- HRes/VRes — значения DPI заголовка; добавляется предупреждение, поскольку некоторые авторы файлов записывают туда не физическое разрешение.
- Encoding=1 — RLE, 0 — без сжатия; другое значение выводится как неизвестный код.
- BytesPerLine — длина строки ОДНОЙ плоскости с выравниванием, не ширина изображения.
- Для <=4 bpp используется фиксированная таблица заголовка; для 8 bpp одной плоскости проверяется маркер 0x0C за 769 байт до конца файла: после него 768 байт палитры, 256 RGB-записей.

## 5. Быстродействие

Полный file.arrayBuffer() не вызывается. Reader читает Blob.slice с кэшем минимум 16 КБ, проверяет смещения, хранит только текущий блок. Это сокращает запрашиваемый объём на больших JPEG по сравнению с декодированием. Для файла меньше 16 КБ кэш может прочитать файл целиком.

Workers работают независимо, свободный worker получает следующее задание. Количество активных заданий ограничено размером пула. В UI результаты приходят партиями раз в 100 мс. В DOM нет 100 000 строк: высота виртуального полотна равна n×46 px, рендерится видимый диапазон с запасом.

При этом список File, результаты и дополнительные поля (включая DQT) хранятся в RAM, поэтому память растёт O(n). Фильтрация и сортировка выполняются в главном потоке, и на очень больших списках могут давать задержку. Индексация каталогов браузером, оперативная память, диск и реализация browser Blob влияют на результат; гарантированное время не заявляется.

«Прочитано байт» — сумма длин срезов, загруженных Reader, не профилирование физического диска. Таймер измеряет Engine после формирования списка; не включает диалог выбора, браузерный обход каталога, подготовку очереди, реактовскую отрисовку после последнего результата и просмотр картинки.

## 6. Надёжность и ограничения

- Проверяются длины и смещения; ограничения на число блоков препятствуют бесконечным циклам.
- Формат определяется содержимым, не расширением.
- Ошибка парсера отображается отдельно для каждого файла.
- Разбор заголовка не является полной проверкой целостности пикселей: файл с валидным заголовком и повреждённым растром может дать метаданные.
- Веб-приложение не читает каталоги без разрешения пользователя и не знает абсолютные пути.
- Превью зависит от браузера. Отсутствие декодера TIFF/PCX не мешает их бинарному разбору.
